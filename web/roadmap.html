How user preference becomes a ranklist

The ranklist should guide prioritization, not replace technical judgment. A popular feature still needs feasibility, governance review, and measurable acceptance criteria.

01

Signal interest

Click a roadmap card to open a prefilled GitHub issue. Users can also comment on SourceForge using the feature name.

02

Describe the workflow

The most useful signals include input type, expected output, hardware, privacy constraints, and why the current app does not solve it yet.

03

Collect evidence

Repeated requests, concrete examples, test files, and community prototypes move an idea higher than generic interest alone.

04

Publish the shortlist

Release planning can publish the top candidates with feasibility notes, risks, and what must be validated before implementation.

Implementation discipline

How 3.7 reached release-candidate validation

The 3.7 foundations passed product, technical, governance, and packaged-application validation. Future candidates begin this process again; no roadmap card inherits release status.

Step 1

Schemas and review gates — complete

EDL JSON, processing report JSON, output profiles, transcript timestamp mapping, history, and privacy flags are implemented.

Step 2

Minimum reviewable workflow — complete

Upload, transcribe, select words, preview cut/mute proposals, accept/reject, undo/redo, export EDL, render audio, and generate the report are connected.

Step 3

Regression and release-candidate validation — complete

Validate duration drift, loudness, sample rate, edit counts, engines, profile overrides, external-service enforcement, accessibility, and packaged macOS behavior.

Step 4

Evidence-led release communication — complete

Release notes distinguish delivered behavior, optional execution boundaries, human-review requirements, and future research.

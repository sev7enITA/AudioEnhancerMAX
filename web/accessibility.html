Accessibility statement

Progress without inflated claims

AudioEnhancerMAX aims to support different ways of seeing, hearing and operating the interface. This page records current foundations, known gaps and the evidence required before declaring conformance.

01 / Commitment

Accessibility is a product requirement

The project treats accessibility as part of functional quality, not as a marketing badge. Interface changes should preserve keyboard operation, readable text, programmatic labels, visible focus and alternatives to color-only status.

No formal conformance claim is made today.

The application has not yet completed the manual assistive-technology and end-to-end workflow testing needed to claim WCAG conformance or specific App Store accessibility support categories.

02 / Foundations

What is already designed into the public pages

Keyboard focus Interactive links expose a visible focus indicator and the information pages provide a skip link.
Semantic structure Headings, landmarks, navigation labels, lists and tables are represented in document structure.
Status in text Important state and governance information is expressed with words rather than color or icon alone.
Responsive layout Pages reflow for narrow screens and avoid viewport-based font scaling for interface labels.
Reduced motion Information pages disable smooth scrolling when the operating system requests reduced motion.
Printable information Support, privacy and accessibility pages include a simplified print presentation.

These foundations do not establish accessibility of every application workflow. The processing workspace has a wider interaction surface and must be assessed separately.

03 / Limitations

Areas that still require evidence

  • Complete VoiceOver navigation through file import, waveform controls, processing settings, progress reporting and export.
  • Keyboard-only operation of all custom controls, tabs, dialogs and dynamic status regions.
  • Accessible alternatives for waveform and monitoring visualizations.
  • Contrast validation across every state, including disabled controls, errors and chart labels.
  • Behavior at larger macOS text sizes and with display zoom.
  • Captions or equivalent text for any future product preview video.

The App Store accessibility questionnaire should remain conservative until these workflows have been tested in the exact submitted build.

04 / Verification

How claims will be earned

The release process should combine automated markup checks with manual keyboard navigation, VoiceOver review, zoom and contrast inspection, reduced-motion testing and task-based testing with users where feasible.

Findings should be recorded against a specific app version and workflow. A capability will be declared in App Store Connect only when it works throughout the relevant user journey, not because one screen contains a compatible control.

05 / Feedback

Report an accessibility barrier

Describe the task, app version, macOS version, assistive technology and the result you expected. Do not include private recordings or personal data in the public issue.
